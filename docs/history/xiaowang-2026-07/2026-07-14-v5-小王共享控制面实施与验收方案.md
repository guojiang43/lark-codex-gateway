## 1. 结论

要让飞书对话无需重启就出现在 MacBook Codex Desktop，必须共享“正在运行的控制面”，而不只是共享 thread rollout 文件。最终链路为：

```text
飞书
  -> M4 唯一网关
  -> 反向 SSH
  -> codex app-server proxy（WebSocket 字节流）
  -> MacBook managed daemon / control socket
     -> Codex Desktop
     -> 小王 MacBook worker
```

Desktop 和小王是同一个 app-server 的两个客户端。M4 仍是唯一飞书入口，MacBook 休眠时不会导致机器人整体失联；MacBook worker 不可用时仍可切回 M4。

## 2. 为什么重启后才看见

此前小王和 Desktop 各自启动独立 app-server。两者写入同一份本地 rollout，所以 Desktop 完整重启、重新读取磁盘后能看到飞书消息；但正在运行的 Desktop 只订阅自己的 app-server 事件，不会监听另一进程写文件。这不是深链或消息落盘失败，而是控制面分裂。

## 3. 实施口径

### MacBook

- managed standalone：`~/.codex/packages/standalone/current/codex`
- control socket：`~/.codex/app-server-control/app-server-control.sock`
- daemon 生命周期：由 `codex app-server daemon bootstrap` 管理
- Desktop 接入：登录环境变量 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1`
- 环境持久化：`~/Library/LaunchAgents/com.john.codex-desktop-daemon-env.plist`

### M4

- 保持唯一飞书 WebSocket 消费者；
- MacBook worker 通过反向 SSH 执行 `codex app-server proxy`；
- proxy 使用 WebSocket framing，不能按 JSONL stdio 解析；
- proxy 或 daemon 不可用时回退独立 stdio，并明确降级原因。

## 4. 产品行为

- 飞书发出的 user message 应实时出现在同一个 Desktop task；
- commentary 只在飞书流式阶段显示，reasoning 不外显；
- 首个 `final_answer` 到达后替换过程区，完成卡只保留结论；
- 完成态不保留“停止生成”或“选择 Session”按钮；
- Session 列表来自目标执行主机的真实 `thread/list`；
- MacBook 离线不自动把同一消息在 M4 重放，避免重复执行。

## 5. 验收顺序

1. John 主动重启 Codex Desktop；
2. 确认 Desktop 未再启动独立 `app-server --stdio`，managed daemon 保持 running；
3. 在飞书当前 MacBook Session 发送一条带两段以上输出的测试消息；
4. 不点击深链、不再次重启，确认 Desktop 当前 task 实时出现 user message 和输出；
5. 确认飞书运行期换行正确、完成后只保留最终答案且按钮消失；
6. 再测 MacBook worker 断开、M4 网关保持在线和切回 M4。

## 6. 升级风险与回滚

`CODEX_APP_SERVER_USE_LOCAL_DAEMON` 是当前 Desktop 安装包中的内部开关，不属于公开稳定接口。Desktop/Codex 升级后必须复验版本探测、socket 和 UI 实时同步。

回滚 Desktop 接入：

```bash
launchctl unsetenv CODEX_APP_SERVER_USE_LOCAL_DAEMON
launchctl bootout gui/$(id -u)/com.john.codex-desktop-daemon-env
```

回滚不会删除 thread、rollout、网关 SQLite 或 managed standalone；M4 网关自动回退 stdio，保留可用性。
