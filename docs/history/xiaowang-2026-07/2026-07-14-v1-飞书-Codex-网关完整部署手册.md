## 0. 一句话结论

这套方案不是“让机器人调用一次模型”，而是让飞书成为本地 Codex 的远程入口：飞书消息进入指定 Codex thread，过程以卡片流式显示，最终只保留结论；同一个 thread 可以继续在 Mac 上的 Codex Desktop 中查看和对话。

部署时必须守住三条原则：

1. 一个飞书应用同一时刻只能有一个网关消费长连接；
2. Desktop 与远程 worker 要实时看到同一轮对话，必须连接同一个 Codex app-server 控制面；
3. 双设备时，永远在线的机器负责飞书入口，可能休眠的笔记本只做可选执行节点。

## 1. 能力范围

当前实现提供：

- 飞书单聊消息进入指定本地 Codex workspace；
- 复用、新建、切换、重命名、归档 Codex Session；
- 运行中添加“处理中”表情，完成后自动移除；
- Card 2.0 同卡流式更新；
- 运行中展示 commentary，不展示 reasoning；
- 收到 final answer 后收起过程，只保留最终答案；
- 停止生成、一次性 command/file/permission 审批；
- 图片和文件受控下载、大小限制与临时文件清理；
- SQLite 幂等、队列、重启恢复和残留 reaction 清理；
- 单设备运行；
- 双设备下由常开 Mac mini 接收飞书，MacBook 醒着时作为 Codex worker；
- 双设备的 Session 按宿主机隔离，不把两台机器的本地 thread 冒充为同一个 Session。

## 2. 总体架构

### 2.1 单设备

```text
飞书客户端
  ↕ 长连接事件 / 回调
同一台 Mac
  ├─ 飞书网关 LaunchAgent
  ├─ SQLite 状态库
  ├─ Codex managed daemon
  └─ Codex Desktop
```

适合：只有一台常开的 Mac mini、Mac Studio，或可以接受“电脑休眠后机器人离线”的个人用户。

代价：这台机器休眠、关机或退出用户登录会话时，飞书入口和执行能力同时离线。

### 2.2 双设备

```text
飞书客户端
  ↕ 长连接事件 / 回调
常开设备（Gateway Host，例如 M4 Mac mini）
  ├─ 唯一飞书网关
  ├─ SQLite 状态库
  ├─ 本机 Codex fallback
  └─ SSH → 127.0.0.1:19022
          ↑ MacBook 主动建立反向隧道
MacBook（Worker Host）
  ├─ 回环 sshd，只监听 127.0.0.1
  ├─ Codex managed daemon / control socket
  └─ Codex Desktop
```

适合：需要机器人 7×24 小时在线，同时又希望任务能进入日常使用的 MacBook Codex Desktop。

关键点：切换的是“执行主机”，不是飞书网关。MacBook 休眠时，Mac mini 仍能接收飞书消息，也能让用户切回本机执行。

## 3. 选型

| 维度 | 单设备 | 双设备 |
| --- | --- | --- |
| 部署复杂度 | 低 | 中高 |
| 机器人在线性 | 取决于该设备是否常开 | 常开网关可持续在线 |
| Desktop 实时同步 | 使用共享 daemon 时支持 | MacBook worker 使用共享 daemon 时支持 |
| 故障隔离 | 飞书入口与执行一起故障 | MacBook 故障不影响飞书入口 |
| SSH 配置 | 不需要 | 需要反向隧道与回环 sshd |
| 推荐对象 | 常开单机用户 | Mac mini + MacBook 用户 |

推荐顺序：

- 有常开台式 Mac：先做单设备；
- 日常工作主要在 MacBook，但需要机器人一直在线：做双设备；
- 只有 MacBook：可以单设备部署，但必须接受休眠期间无法收发消息。

## 5. 飞书开放平台后台配置

入口：[飞书开放平台](https://open.feishu.cn/app)。

### 5.1 创建应用并开启机器人

1. 创建“企业自建应用”；
2. 添加“机器人”能力；
3. 配置机器人名称、头像和描述；
4. 记录 App ID；
5. App Secret 只写入目标机器的 Keychain 或 `0600` 文件，不放进 Git、文档、SQLite 或日志。

飞书发送消息接口要求应用开启机器人能力，接收者还必须在应用可用范围内。[官方说明](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)

### 5.2 最小权限

在“开发配置 → 权限管理”中申请：

| 用途 | Scope | 必需性 |
| --- | --- | --- |
| 接收机器人单聊消息 | `im:message.p2p_msg:readonly` | 必需 |
| 以机器人身份发送消息 | `im:message:send_as_bot` | 必需 |
| 添加、删除“处理中”表情 | `im:message.reactions:write_only` | 必需 |
| 下载消息中的图片和文件 | `im:message:readonly` | 使用附件时必需 |
| 创建、流式更新 Card 2.0 | `cardkit:card:write` | 必需 |

如果要在群聊中只处理 @ 机器人的消息，再申请：

```text
im:message.group_at_msg:readonly
```

不要为了省事申请“获取群组中所有消息”敏感权限，除非产品确实要处理未 @ 机器人的全部群消息。

权限依据：

- [接收消息事件](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive.md)
- [发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)
- [获取消息资源](https://open.feishu.cn/document/server-docs/im-v1/message/get-2.md)
- [添加消息表情回复](https://open.feishu.cn/document/server-docs/im-v1/message-reaction/create.md)
- [创建卡片实体](https://open.feishu.cn/document/cardkit-v1/card/create.md)

### 5.3 事件订阅

在“事件与回调 → 事件配置”中：

1. 选择“使用长连接接收事件”；
2. 添加 `im.message.receive_v1`；
3. 添加 `application.bot.menu_v6`。

长连接由飞书 SDK 主动建立，不需要公网域名、Webhook 或端口映射。[官方说明](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case.md)

机器人自定义菜单事件本身不需要额外 scope；只有读取操作者姓名时才需要可选字段权限，当前网关只使用 `open_id`。[官方说明](https://open.feishu.cn/document/client-docs/bot-v3/events/menu.md)

### 5.4 回调订阅

在“事件与回调 → 回调配置”中：

1. 选择“使用长连接接收回调”；
2. 添加新版卡片交互回调 `card.action.trigger`；
3. 不配置旧版卡片回调 URL。

卡片按钮需要在约 3 秒内返回交互响应，因此网关只确认操作，耗时任务继续异步执行。[官方说明](https://open.feishu.cn/document/feishu-cards/card-callback-communication.md)

### 5.5 机器人自定义菜单

开启自定义菜单，悬浮菜单或可切换菜单均可。所有子菜单的响应动作选择“推送事件”，不要选择“发送文字消息”。

| 主菜单 | 子菜单 | 事件 key |
| --- | --- | --- |
| 会话 | 新建会话 | `new_session` |
| 会话 | 切换会话 | `session_select` |
| 会话 | 当前会话 | `session_current` |
| 管理 | 重命名会话 | `session_rename` |
| 管理 | 归档会话 | `session_archive` |
| 管理 | 运行状态 | `current_status` |
| 控制 | 停止生成 | `stop_generation` |
| 控制 | 使用帮助 | `help` |

不要加入“工程任务”“分析任务”“分叉会话”“只读会话”等低频概念。日常产品界面只保留 Session 和执行控制。

### 5.6 可用范围与发布

1. 把实际使用者加入应用可用范围；
2. 创建新版本；
3. 核对新增权限、事件、回调和菜单；
4. 提交审核或由企业管理员发布；
5. 等待新版本生效后再测试菜单。

“后台保存成功”不等于客户端生效。未发布版本时，菜单、权限和事件配置可能仍使用旧版本。

### 5.7 获取授权用户 open_id

网关使用应用维度的 `open_id` 做白名单。推荐通过以下任一方式获取：

- 在开发者后台事件调试中查看该用户发送的 `im.message.receive_v1` 事件，读取 `sender.sender_id.open_id`；
- 使用同一个飞书应用通过通讯录接口按邮箱或用户定位，再读取该应用视角下的 `open_id`。

不要把别的飞书应用中的 `open_id` 直接复用；同一用户在不同应用下的 open_id 可能不同。

## 9. Codex managed daemon 与 Desktop 共享控制面

### 9.1 为什么必须共享 daemon

两个独立 `codex app-server --stdio` 可以写入同一份 thread rollout，但当前 Desktop 不会自动收到另一个进程的事件。表现是：飞书任务已经落盘，只有重启 Desktop 后才看见。

正确形态是 Desktop 和网关 worker 同时连接一个 Unix control socket。

Codex 官方 app-server 用于富客户端集成，提供 thread、turn、审批和流式事件；stdio 使用 JSONL，Unix socket 使用 WebSocket Upgrade。[Codex App Server 官方说明](https://learn.chatgpt.com/docs/app-server.md)

### 9.2 安装 standalone

官方无人值守安装命令：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | CODEX_NON_INTERACTIVE=1 sh
```

安装器把可见命令放进 `~/.local/bin`，版本包放在 `~/.codex/packages/standalone`。[官方环境变量说明](https://learn.chatgpt.com/docs/config-file/environment-variables.md)

首次部署建议先在交互终端运行 `codex`，确认登录状态和 workspace 访问正常，再启动后台服务。

### 9.3 启动 managed daemon

```bash
~/.local/bin/codex app-server daemon bootstrap
~/.local/bin/codex app-server daemon version
```

期望 `version` 返回：

```json
{
  "status": "running",
  "socketPath": "/Users/<user>/.codex/app-server-control/app-server-control.sock",
  "cliVersion": "<version>",
  "appServerVersion": "<version>"
}
```

远程或本地 worker 使用：

```bash
codex app-server proxy
```

`proxy` 代理的是 WebSocket 字节流，不是每行一条 JSON 的 JSONL。客户端必须对 `ws://codex-app-server/rpc` 做 WebSocket 握手。

### 9.4 让 Desktop 接入同一 daemon

当前已验证的 Codex Desktop 版本会在启动时读取：

```text
CODEX_APP_SERVER_USE_LOCAL_DAEMON=1
```

先为当前登录会话设置：

```bash
launchctl setenv CODEX_APP_SERVER_USE_LOCAL_DAEMON 1
```

再安装一个用户级 LaunchAgent，在登录时执行同一条 `launchctl setenv`。设置完成后，由用户主动退出并重新打开 Codex Desktop。

重要边界：这个变量来自当前 Desktop 安装包内部实现，不在公开稳定环境变量清单中。每次 Codex Desktop 大版本升级后都要重新验证。失效时不会丢 thread，但 Desktop 可能退回“重启后才看到外部 turn”。

### 9.5 验证共享控制面

```bash
launchctl getenv CODEX_APP_SERVER_USE_LOCAL_DAEMON
codex app-server daemon version
ps -axo pid,ppid,etime,command | grep 'codex app-server'
lsof -n -U | grep app-server-control
```

通过标准：

- 环境变量为 `1`；
- daemon 为 `running`；
- Desktop 重启后没有自己的 `app-server --stdio`；
- Desktop 与 worker 都连接同一个 control socket。

## 10. 单设备部署

### 10.1 标准步骤

1. 完成飞书后台配置并发布；
2. 完成仓库参数化；
3. 安装依赖并通过基础验证；
4. 将 App Secret 写入 Keychain；
5. 安装 Codex managed daemon；
6. 配置 Desktop 使用 local daemon；
7. 将网关本机 Codex connector 配置为 `codex app-server proxy`；
8. 安装网关 LaunchAgent；
9. 验证飞书消息、卡片和 Desktop 实时同步。

### 10.2 当前仓库的实际支持程度

当前仓库的默认本机 connector 仍使用 stdio；WebSocket proxy 已在 `AppServerClient` 中实现，但“本机使用 proxy”的安装开关尚未做成通用配置。

因此有两种口径：

- 不要求 Desktop 实时出现飞书 turn：当前代码可直接单机运行；
- 要求完整实时同步：部署前需增加一个本机 transport 配置，让主机连接 `codex app-server proxy`，不能继续使用独立 stdio。

这不是架构不支持，而是当前安装器还没有把已验证的 proxy 能力暴露成单机配置项。给同事承诺“一键单机完整同步”前，应先补这个参数化工作。

### 10.3 安装网关 LaunchAgent

  '/absolute/path/to/workspace' \

查看状态：

## 11. 双设备部署

以下形态已在真实环境验收。

### 11.1 角色分工

- Gateway Host：常开 Mac mini，持有飞书 App Secret、SQLite 和唯一飞书 WebSocket；
- Worker Host：MacBook，持有 Codex 登录态、workspace 和 Desktop；
- MacBook 主动向 Mac mini 建立反向隧道，避免要求 MacBook 有公网入口；
- Mac mini 只能通过回环地址访问反向端口。

### 11.2 准备 SSH 密钥

在 Gateway Host 生成专用密钥，不复用个人通用密钥：

```bash
ssh-keygen -t ed25519 -f ~/.ssh/xiaowang-worker -N ''
```

把公钥安全传到 Worker Host。私钥留在 Gateway Host，权限保持 `0600`。

在 Worker Host 的 `~/.ssh/config` 或等价配置中，准备一个能主动连接 Gateway Host 的 SSH host alias，例如：

```sshconfig
Host gateway-mini
  HostName <gateway-address>
  User <gateway-user>
  IdentityFile ~/.ssh/<worker-to-gateway-key>
  ServerAliveInterval 15
  ServerAliveCountMax 3
```

### 11.3 Worker Host 安装回环 sshd 与反向隧道

在 Worker Host：

```bash
./scripts/install-macbook-worker-tunnel.zsh \
  '/path/to/gateway-public-key.pub' \
  'gateway-mini'
```

脚本会安装两个 LaunchAgent：

- `com.example.xiaowang-codex-worker-sshd`：只监听 Worker 的 `127.0.0.1:19022`；
- `com.example.xiaowang-codex-worker-tunnel`：把该端口反向映射到 Gateway 的 `127.0.0.1:19022`。

sshd 安全限制包括：公钥认证、禁用密码、禁用 TTY、禁用 agent forwarding、禁用 TCP forwarding、禁用 root。

### 11.4 Worker Host 安装 shared daemon

在 Worker Host 完成第 9 节全部步骤，并重启 Codex Desktop。先确认：

```bash
codex app-server daemon version
launchctl getenv CODEX_APP_SERVER_USE_LOCAL_DAEMON
```

### 11.5 Gateway Host 配置

在 Gateway Host：

```bash
./scripts/setup-keychain-secret.zsh
./scripts/install-launch-agent.zsh \
  '/absolute/path/on/gateway' \
  '/absolute/path/on/worker' \
  'stable-project-id'
```

同时配置：

```text
XIAOWANG_MACBOOK_SSH_USER=<worker-user>
XIAOWANG_MACBOOK_SSH_HOST=127.0.0.1
XIAOWANG_MACBOOK_SSH_PORT=19022
XIAOWANG_MACBOOK_CODEX_BIN=<worker-standalone-or-app-codex-path>
```

Gateway 通过以下逻辑连接 Worker：

```text
ssh -p 19022 <worker-user>@127.0.0.1 codex app-server proxy
```

proxy 失败时，网关保持飞书入口在线并按当前实现降级到独立 stdio；不能把同一条消息静默改在另一台机器执行，否则可能重复写文件或执行命令。

### 11.6 双设备验证

Worker Host：

```bash
launchctl print gui/$(id -u)/com.example.xiaowang-codex-worker-sshd
launchctl print gui/$(id -u)/com.example.xiaowang-codex-worker-tunnel
codex app-server daemon version
```

Gateway Host：

```bash
launchctl print gui/$(id -u)/com.example.xiaowang-codex-gateway
ps -axo pid,ppid,etime,command | grep 'app-server proxy'
tail -n 100 <gateway-root>/.data/gateway.stderr.log
```

通过标准：

- 唯一网关 `state = running`；
- 日志出现 `feishu_ws_ready`；
- Gateway Host 存在一条到 Worker 的 `app-server proxy` SSH 进程；
- Worker daemon control socket 同时被 Desktop 和 proxy 连接；
- 飞书发送消息后，不重启 Desktop 就能在当前 task 中看到。

## 12. 飞书端验收清单

按顺序验收：

1. 点击“运行状态”，确认网关和执行主机在线；
2. 点击“当前会话”，确认显示正确 thread 和主机；
3. 点击“切换会话”，确认列出目标 workspace 的真实 Session；
4. 发送一条短消息，确认原消息出现“处理中”表情；
5. 生成过程中确认同一卡片流式更新且段落换行正常；
6. 生成完成后确认表情消失、停止按钮消失、只保留最终答案；
7. 不重启 Desktop，确认飞书 user message 和回答实时出现在同一 task；
8. 发送长任务并点击“停止生成”；
9. 触发 command/file approval，分别测试“允许一次”和“拒绝”；
10. 单机或 Gateway Host 发送图片/文件，确认读取和临时文件清理；
11. 双设备断开 Worker 隧道，确认飞书入口仍在线且可以切回 Gateway Host。

## 13. 运维

### 13.1 网关状态

```bash
launchctl print gui/$(id -u)/com.example.xiaowang-codex-gateway
```

### 13.2 重启网关

先确认没有活动 run，再执行：

```bash
launchctl kickstart -k gui/$(id -u)/com.example.xiaowang-codex-gateway
```

不要在生成中途重启。启动恢复会把遗留的活动 run 收口为失败，不会自动重放，以免重复执行。

### 13.3 日志

```bash
tail -n 100 <gateway-root>/.data/gateway.stderr.log
tail -n 100 <gateway-root>/.data/gateway.stdout.log
```

### 13.4 状态库

SQLite 位于：

```text
<gateway-root>/.data/gateway.db
```

备份时应先停止网关，或者同时复制 WAL/SHM 文件。不要只复制正在运行数据库的主文件后宣称备份完成。

### 13.5 Codex daemon

```bash
codex app-server daemon version
codex app-server daemon restart
codex app-server daemon stop
```

daemon 重启会影响 Desktop 和远程 worker，应安排在没有活动 turn 的窗口。

### 13.6 卸载网关

```bash
./scripts/uninstall-launch-agent.zsh
```

该脚本移除常驻注册，不删除 SQLite 和日志。

## 14. 常见故障

| 现象 | 最可能根因 | 检查方式 |
| --- | --- | --- |
| “回调服务不在线” | 网关 LaunchAgent 不在线，或后台未选择长连接 | `launchctl print`、检查 `feishu_ws_ready` |
| 菜单点击无响应 | `application.bot.menu_v6` 未订阅、响应动作不是推送事件、版本未发布 | 后台事件和版本记录 |
| 卡片按钮无响应 | 未配置 `card.action.trigger` 长连接回调 | 后台回调配置、interaction_events |
| 切换 Session 看不到现有任务 | workspace `cwd` 不一致，或当前选择了另一台主机 | `thread/list`、workspace 绝对路径 |
| 飞书消息重启 Desktop 后才出现 | Desktop 与 worker 使用两个独立 app-server | daemon、进程树、Unix socket |
| MacBook 显示离线 | 反向隧道、回环 sshd 或 daemon 中断 | 两个 worker LaunchAgent、M4 proxy 进程 |
| 同一条消息回复两次 | 同一个飞书应用运行了两个网关消费者 | 所有设备进程和 LaunchAgent |
| 完成后仍有停止按钮 | CardKit 最终全量更新失败 | 网关日志、卡片 update 响应 |
| 卡片返回 `300301` | `element_id` 重复、超长或格式非法 | 所有 element ID 唯一且不超过 20 字符 |
| 任务执行失败但没有 turn ID | thread resume/start 之前失败 | runs 表、app-server 错误日志 |
| 图片或文件失败 | 缺少 `im:message:readonly`、资源不属于消息、超过本地 25 MB 限制 | 飞书错误码、attachment 日志 |

## 15. 安全底线

- 默认只接受一个允许的 `open_id`；
- 默认使用机器人单聊；启用群聊时只订阅 @ 消息；
- App Secret 只存 Keychain 或 `0600` 文件；
- 不把 access token、auth state、`~/.codex` 整目录同步到另一台机器；
- 网关 project 路径由服务端配置，用户消息不能指定本地路径；
- Worker sshd 只监听 `127.0.0.1`；
- 双设备使用专用 SSH 密钥；
- 不开放未认证的非回环 WebSocket；
- 审批只提供“允许一次/拒绝”，不提供永久授权；
- 同一个飞书应用只运行一个事件消费者；
- 日志不得记录 App Secret、token 或完整私密附件内容。

Codex 官方明确将非回环 WebSocket 视为需要认证和 TLS 的边界；本方案用 Unix socket 和 SSH 转发，不把 app-server 暴露到公网。[官方说明](https://learn.chatgpt.com/docs/app-server.md)

## 16. 当前已知边界

1. 当前实现和安装脚本仅面向 macOS；
2. 当前代码库仍有部署者专属常量，交给同事前必须参数化；
3. 单设备的“本地 proxy”能力已经在客户端层实现并验证，但还没有做成通用安装开关；
4. `CODEX_APP_SERVER_USE_LOCAL_DAEMON` 是 Desktop 内部开关，不是公开稳定配置；
5. 双设备下 MacBook Session 的远程附件复制尚未完成，当前应明确拒绝并提示切到 Gateway Host；
6. MacBook 休眠时 worker 离线是正常现象，不能假装仍然可用；
7. Codex、飞书 SDK 或 CardKit 升级后，需要重跑协议、测试和真实飞书验收。
