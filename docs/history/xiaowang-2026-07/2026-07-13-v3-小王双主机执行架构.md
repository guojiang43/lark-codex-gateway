# 小王双主机执行架构

- 版本：v3
- 日期：2026-07-13
- 状态：文本链路已部署，等待飞书端交互验收；远端附件传输待实现
- 替代范围：替代 v2 中“网关跟随 Codex 宿主机运行”的假设

## 1. 结论

小王不做双活飞书网关，也不在 M4 与 MacBook 之间切换飞书长连接。

最终架构为：

- **M4 Mac mini：永久在线的飞书入口、控制面和兜底 Codex 执行节点。**
- **MacBook：醒着时可选的 Codex 执行节点，不直接连接飞书。**
- 飞书卡片切换的是“执行主机”，不是“网关主机”。
- M4 永远能收到菜单、消息和卡片回调，因此 MacBook 休眠时仍能解释状态并提供恢复动作。

## 2. 为什么不能双网关

飞书长连接的多客户端语义是集群随机分发，不是广播。同一应用同时建立多个长连接时，每个事件只会随机投递给其中一个客户端。

因此双网关会产生三个不可接受的问题：

1. 消息随机落到 M4 或 MacBook，执行环境不可预测；
2. Session 列表与当前 Session 随宿主机漂移；
3. MacBook 休眠后，用户甚至无法通过飞书按钮把入口切回 M4。

所以必须把“永远在线的入口”和“可切换的执行节点”拆开。

## 3. 目标链路

```text
飞书用户
   │
   ▼
M4 小王 Gateway（唯一 Feishu WebSocket）
   │
   ├── 执行主机 = M4 ─────► M4 Codex app-server
   │
   └── 执行主机 = MacBook ─► 反向 SSH 通道 ─► MacBook Codex app-server
                                      ▲
                                      └── MacBook 醒着时主动建立
```

M4 负责：

- 接收并幂等处理飞书消息、菜单和卡片回调；
- 创建与流式更新 CardKit 卡片；
- reaction、审批、停止生成和最终收口；
- 保存当前聊天选择的执行主机；
- 检测 MacBook worker 在线状态；
- 在 MacBook 离线时返回可操作的状态卡，而不是让消息失联。

MacBook 负责：

- 运行仅绑定本机回环地址的受控 SSH/Codex worker；
- 醒着时主动向 M4 建立反向 SSH 隧道；
- 通过 stdio 运行本机 Codex app-server；
- 只暴露 Codex 协议，不保存或消费飞书 App Secret。

## 4. 主机切换语义

“当前状态”卡片增加：

- 当前网关：M4（固定）
- 当前执行主机：M4 / MacBook
- MacBook 状态：在线 / 离线 / 协议不可用
- 按钮：`切换到 MacBook` 或 `切换到 M4`

切换到 MacBook 前必须实时检查：

1. 反向 SSH 端口存在；
2. MacBook Codex app-server 能完成 initialize；
3. 目标工作区存在；
4. `thread/list` 能正常返回。

任一条件失败，选择不生效，并返回具体原因。

## 5. MacBook 离线时的行为

MacBook 休眠、关机、断网或隧道中断时：

- M4 飞书网关继续在线；
- 不把 MacBook Session 静默映射成 M4 Session；
- 不自动在 M4 重放已发给 MacBook 的未完成任务；
- 新消息若仍选择 MacBook，返回“MacBook 离线”卡片；
- 卡片提供“改在 M4 执行”和“稍后重试”；
- 只有 John 明确点击后，后续消息才使用 M4 Session。

不自动故障转移的原因是两台机器的本地文件、未提交改动、Codex thread 和权限上下文不同。自动换机器可能在错误环境执行写操作。

## 6. Session 规则

- Session 必须带 `host_id`，取值为 `m4` 或 `macbook`；
- Session 选择卡只展示当前执行主机的 Session；
- 切换执行主机后，恢复该主机上次绑定的 Session；没有绑定时选择该主机最近的本地 Session；
- 不跨主机伪造、复制或自动合并 Codex thread；
- 如需把工作从一台机器迁到另一台，应使用显式 handoff，而不是 Session 切换。

## 7. 通道设计

优先复用 Codex app-server stdio 协议，不新增业务 RPC：

1. MacBook 运行仅监听 `127.0.0.1` 的受控 SSH 服务；
2. MacBook LaunchAgent 主动连接 M4，建立反向端口转发；
3. M4 以 SSH 子进程启动 MacBook 的 Codex app-server；
4. 现有 AppServerClient 继续处理 thread、delta、interrupt 和 approval；
5. SSH 子进程退出即视为 MacBook worker 离线，运行中的任务按失败收口，不自动重放。

附件需要单独处理：M4 下载的临时文件不能把本地路径直接传给 MacBook。当前版本会在下载前明确拒绝把附件交给 MacBook Session，提示切换到 M4 或改发纯文字；不会传递错误路径。后续通过同一受控通道复制到 MacBook 临时目录，并在任务结束后两端清理。

## 8. 安全边界

- 飞书 App Secret 最终只保留在 M4；MacBook 完成 worker 化后删除本机副本；
- MacBook SSH worker 只监听回环地址，不开放局域网或公网端口；
- 只接受 M4 专用公钥，关闭密码和交互式认证；
- 反向端口只绑定 M4 的 `127.0.0.1`；
- Codex 工作区由两端配置固定，飞书消息不能传入路径；
- 远端附件目录为 `0700`，文件为 `0600`，任务完成后删除；
- MacBook 离线后不缓存并自动重放写任务。

9. 做在线、隧道断开、睡眠模拟、恢复、停止生成和审批回归。

## 10. 验收标准

- M4 是唯一飞书长连接，MacBook 不连接飞书；
- MacBook 在线时可在卡片切换并看到 MacBook 本地 Session；
- 文本回答保持同卡流式输出；
- MacBook 隧道断开后，小王仍在 3 秒内返回离线状态；
- 离线任务不自动在 M4 执行；
- 点击“改在 M4 执行”后，后续任务使用 M4 Session；
- MacBook 恢复后可重新选择，且原 MacBook Session 仍可见；
- 任意时刻不存在两个飞书事件消费者；
- 两端日志、状态库和配置均不出现飞书 App Secret。
