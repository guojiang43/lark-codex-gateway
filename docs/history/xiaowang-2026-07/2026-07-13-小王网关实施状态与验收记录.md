小王网关当前由 M4 Mac mini 的用户级 LaunchAgent 常驻运行，M4 是唯一飞书 WebSocket 入口和兜底执行节点。MacBook 不再连接飞书，只通过回环 SSH worker 与主动反向隧道向 M4 暴露本机 Codex app-server。飞书卡片切换的是执行主机，不是网关主机。

## 8. 18:04 Session 恢复与发现修复

### 现象

- LaunchAgent 恢复后，用户发送消息得到“任务执行失败，请稍后重试”；
- “切换会话”只展示网关 SQLite 中登记的 Session，看不到宿主机已有 Codex thread。

### 根因

1. 网关重启后直接对旧 thread ID 调用 `turn/start`，没有先调用 `thread/resume`。失败 run 均未产生 `turn_id`，证明失败发生在 turn 创建前。
2. 创建后尚未执行过 turn 的空 Session 没有持久化 rollout；旧 app-server 退出后，其 thread ID 无法从磁盘恢复。
3. Session 选择卡只调用 `StateStore.listSessions()`，没有调用 app-server 已提供的、可按 `cwd` 过滤的 `thread/list`。
4. Codex Session 是宿主机本地状态。M4 无法直接枚举当前 MacBook 的 Desktop Session，跨机器不能伪装成同一 Session。

### 修复

- 每个 run 开始前先 `thread/resume`；
- 空 Session 的 thread 不存在时创建替代 thread，并更新 SQLite 中的 Session 映射；
- 打开 Session 选择卡前，通过 `thread/list` 按 M4 目标 project 的绝对 `cwd` 同步现有 thread；
- 将 app-server 请求错误保留为结构化错误，并记录 `gateway_run_failed`，不再只保存笼统的数据库错误码；
- Codex 协议启动闸门新增 `thread/list` 检查。

### 验证

- 本地与 M4：15 个测试文件、52 个测试通过；typecheck、build 通过；0 个高危审计漏洞；
- M4：同一套标准验证全部通过；

## 13. 2026-07-14 会话呈现与流式卡片收口

### 问题定型

这不是三个独立的视觉问题，而是同一条消息生命周期丢失了 Codex 的结构：

1. M4 通过 SSH 启动的是 MacBook 上第二个 `app-server --stdio`，它会写同一份 thread rollout，但 Codex Desktop 的当前内存控制面不会自动收到另一个进程的事件；
2. 网关只消费 `item/agentMessage/delta` 文本，没有保留 `itemId` 与 `phase`，因此 commentary、不同消息段和 `final_answer` 被拼成一条字符串；
3. CardKit 结束流式时沿用累计字符串，所以过程说明永久留在最终卡片。

### 已上线改动

- 消费 `item/started`，按 `threadId + turnId + itemId` 记录 `commentary / final_answer`；
- 不转发 reasoning 事件；运行中只展示可公开的 commentary；
- 不同 agent message item 之间自动插入两个换行，避免段落粘连；
- 首个 `final_answer` 到达时替换整张卡片正文，结束后只保留最终答案；
- 每轮结束后，通过 M4→MacBook 回环 SSH 执行 `open -g codex://threads/<threadId>`；该命令只能保证深链被系统接受，真实验收已证明它不能可靠刷新当前已打开的 Desktop 任务；
- 已实现优先尝试 `codex app-server proxy`、失败后自动回退 `app-server --stdio`，不因 Desktop 控制面未就绪而破坏现有可用链路。回退模式只保证 turn 写入同一份 rollout，不保证当前 Desktop 窗口可见。

### 共享控制面的当前边界

MacBook 当前 ChatGPT App 自带的 Codex 进程没有创建 `~/.codex/app-server-control/app-server-control.sock`。直接运行 `codex app-server proxy` 的真实错误为“socket 不存在”；运行官方 `codex app-server daemon start` 又因缺少 managed standalone 安装而拒绝启动。因此当前只有“同一 thread 持久化”，没有 Desktop 自动重载或实时同步。

要升级为真正的实时同控制面，需要另行安装官方 managed standalone、启动受管 daemon/control socket，并确认 Codex Desktop 也接入该控制面。该系统级安装不作为本次热修的隐式前置条件。

### 验证与生产状态

- 先跑出 4 个失败用例，分别覆盖 proxy 命令、phase 丢失、卡片无法替换、过程与结论拼接；
- MacBook 与 M4 均通过 21 个测试文件、77 个测试；typecheck、build 通过；生产依赖审计 0 漏洞；
- M4 在 0 个活动 run 时热重启，LaunchAgent 主进程为 `78164`、`last exit code = 0`；
- 日志记录 `macbook_desktop_proxy_unavailable` 后成功进入 `standalone_stdio_with_desktop_refresh`，随后记录 `feishu_ws_ready`；
- M4 经反向 SSH 执行 Desktop thread URL 的命令返回 0，但 10:40 的真实验收证明“命令成功”不等于 Desktop UI 刷新；此前的“验收成功”结论作废。
